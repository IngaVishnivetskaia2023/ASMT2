### What is Head of Line Blocking?

#### General Concept
```
Any ORDERED QUEUE can have HOL:

  [STUCK] [ready] [ready] [ready]
     ↑       ↑       ↑       ↑
   blocked  waits   waits   waits
   
The "head" (first in line) blocks the entire "line" (queue).
```

#### In networking
A situation where a lost, delayed, or slow-processing packet/request 
at the front of an ordered sequence prevents delivery of subsequent packets/requests that are already available and could otherwise be processed.


#### HOL in HTTP 1.1. vs HTTP 2
```
HTTP/1.1: 6 connections × 1 request each
  Packet loss on Connection 3 → only Connection 3 stalls
  Other 5 connections: unaffected (83% throughput)

HTTP/2: 1 connection × all requests multiplexed
  Packet loss on THE connection → ALL streams stall
  Everything waits (0% throughput until retransmit)
```

```
┌─────────────────────────────────────────────────────┐
│  HTTP-level HOL (Application Layer)                  │
│                                                      │
│  Request B waits for Request A to complete           │
│  on the same TCP connection (browser compensate      │
│  by opening 6 connections)                           │
│  [Request A ───── slow ─────────] [Request B] WAITS  │
│                                                      │
│  Present in: HTTP/1.1                                │
│  Solved by:  HTTP/2 (multiplexing)                   │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│  TCP-level HOL (Transport Layer)                     │
│                                                      │
│  TCP guarantees ORDERED delivery.                    │
│  Packet #5 lost → packets #6,7,8 can't be           │
│  delivered to application until #5 retransmitted.    │
│                                                      │
│  [pkt1][pkt2][pkt3][pkt4][✗LOST][pkt6][pkt7]       │
│                              ↑     HELD  HELD        │
│                                                      │
│  Present in: HTTP/1.1 AND HTTP/2                     │
│  Solved by:  HTTP/3 (QUIC over UDP)                  │
└─────────���───────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│  No HOL                                              │
│                                                      │
│  Each stream independently ordered.                  │
│  Loss in stream A — only A waits.                    │
│                                                      │
│  Present in: HTTP/3                                  │
└─────────────────────────────────────────────────────┘
```


### Explain TCP/IP Model

#### Why "TCP/IP"?
Named after the two most important protocols that make the Internet work:

- **IP** — delivers packets to the right machine (addressing)
- **TCP** — makes sure data arrives reliably and in order

They were designed together (1970s, Vint Cerf & Bob Kahn) as the foundation of the Internet. The name stuck even though the model has other protocols too.

```
┌─────────────────────────────────────────────────────┐
│  Layer 4: APPLICATION                                │
│  "What are we communicating?"                        │
│                                                      │
│  HTTP, HTTPS, WebSocket, FTP, SMTP, DNS              │
│  Your code lives here.                               │
├─────────────────────────────────────────────────────┤
│  Layer 3: TRANSPORT                                  │
│  "How do we ensure reliable delivery?"               │
│                                                      │
│  TCP (reliable, ordered)                             │
│  UDP (fast, no guarantees)                           │
│  QUIC (UDP + reliability per stream)                 │
├─────────────────────────────────────────────────────┤
│  Layer 2: INTERNET (Network)                         │
│  "How do we route to the right machine?"             │
│                                                      │
│  IP (addressing: 192.168.1.1 or IPv6)               │
│  Routing between networks                            │
├─────────────────────────────────────────────────────┤
│  Layer 1: NETWORK ACCESS (Link/Physical)             │
│  "How do bits physically travel?"                    │
│                                                      │
│  Ethernet, WiFi, fiber optics, 4G/5G                 │
│  MAC addresses, physical signals                     │
└─────────────────────────────────────────────────────┘
```

TCP/IP is a 4-layer networking model named after its two core protocols: IP handles addressing and routing packets to the right machine, 
TCP handles reliable ordered delivery between applications. Data flows down through Application → Transport → Internet → Link layers on send, 
and back up on receive — each layer adding its own headers for addressing, reliability, and physical transmission."

#### OSI Model

| # | Layer | What It Does | Protocols/Tech | Real-World Terminology You'll Hear |
| :-- | :-- | :-- | :-- | :-- |
| 7 | Application | User-facing communication | HTTP, WebSocket, DNS, FTP, SMTP, gRPC | "Layer 7 load balancer" (NGINX, ALB) — routes by URL/headers |
| 6 | Presentation | Encryption, encoding, compression | TLS/SSL, JSON, UTF-8, gzip, JPEG | "TLS terminates at Layer 6", "SSL offloading" |
| 5 | Session | Connection lifecycle, keep-alive | WebSocket sessions, OAuth tokens, cookies | "Session persistence", "sticky sessions" on LB |
| 4 | Transport | Reliable delivery, ports | TCP, UDP, QUIC | "Layer 4 load balancer" (NLB) — routes by IP+port |
| 3 | Network | Addressing, routing between networks | IP (v4/v6), ICMP, routers | "Layer 3 switch", "IP routing", "VPN operates at L3" |
| 2 | Data Link | Node-to-node, error detection | Ethernet, WiFi (802.11), MAC addresses, switches | "Layer 2 switch", "VLAN", "MAC filtering" |
| 1 | Physical | Raw bits transmission | Cables, fiber, radio waves, electrical signals | "Layer 1 issue" = cable unplugged, hardware failure |




### Explain REST and RESTful

**REST (Representational State Transfer)** — an architectural style (set of constraints) for designing networked APIs, defined by Roy Fielding in 2000.

**RESTful** — an API that follows REST constraints.

| Constraint | Meaning | Practical Impact |
| :-- | :-- | :-- |
| Client-Server | Client and server are independent | Frontend and backend evolve separately |
| Stateless | Each request contains ALL info needed; server stores no session | No server-side session; send token with every request |
| Cacheable | Responses must declare if cacheable | HTTP cache headers (ETag, Cache-Control) |
| Uniform Interface | Standardized way to interact with resources | URLs = nouns, HTTP methods = verbs |
| Layered System | Client doesn't know if talking to server or proxy | CDN, load balancers, gateways transparent |
| Code on Demand (optional) | Server can send executable code | JavaScript served by server |

```
Representational: Server sends a REPRESENTATION of resource
                  (JSON, XML — not the database record itself)

State:            The current state of the resource

Transfer:         Transferred from server to client (or vice versa)

→ "Transfer representations of resource state between client and server"
```


### Richardson Maturity Model

```
Level 3: HATEOAS          ← Truly RESTful (almost nobody)
Level 2: HTTP Verbs       ← Most "REST APIs" stop here
Level 1: Resources        
Level 0: The Swamp of POX
```


| Level | Name | Description | Example |
| :-- | :-- | :-- | :-- |
| 0 | Swamp of POX | One URL, one method, RPC-style | POST /api with {action: "getUser", id: 42} |
| 1 | Resources | Separate URLs per resource, but only POST | POST /api/users/42 POST /api/orders/5 |
| 2 | HTTP Verbs | Resources + proper methods + status codes | GET /api/users/42 DELETE /api/orders/5 → 204 |
| 3 | HATEOAS | Responses contain links to possible next actions | Response includes "links": { "cancel": ..., "pay": ... } |


#### Practical Reality
```
Level 0: Legacy SOAP, some internal tools
Level 1: Poorly designed APIs
Level 2: 95% of production "REST" APIs ← you're here
Level 3: Some enterprise APIs, rarely in frontend world

Most teams aim for Level 2 and call it "RESTful."
Level 3 adds complexity with little practical benefit
for typical SPA ↔ Backend communication
(frontend already knows the routes).
```

### Is REST is protocol-agnostic?

Technically yes — REST is protocol-agnostic. Fielding defined it as **an architectural style (constraints)**, 
not as "HTTP API." But in practice, HTTP is the only protocol that naturally satisfies REST constraints.

But most likely HTTP was designed with REST in mind (Fielding co-authored HTTP/1.1 AND defined REST).

```
REST Constraint          HTTP has it built-in
──────────────────       ──────────────────────
Uniform interface   →    Methods (GET, POST), URIs, headers
Stateless           →    Each request independent by design
Cacheable           →    Cache-Control, ETag headers
Layered             →    Proxies, CDNs work transparently
Resource-based      →    URLs = resource identifiers
Self-descriptive    →    Content-Type, status codes
```

#### Contrast with Alternatives That ARE Protocol-Bound

| Style | Bound to Protocol? |
| :-- | :-- |
| REST | No (style) — but practically HTTP only |
| GraphQL | No (spec) — but practically HTTP only |
| gRPC | Yes — HTTP/2 specifically |
| SOAP | No (spec) — HTTP or SMTP or anything with envelope |



### Does gRPC bound to HTTP2?

gRPC did NOT exist before HTTP/2. It was designed by Google in 2015 — the same year HTTP/2 was standardized. 
It was built FROM SCRATCH to exploit HTTP/2 features.

```
gRPC needs features that ONLY HTTP/2 provides:

┌────────────────────────┬──────────────────────────────────┐
│ gRPC Feature           │ Requires HTTP/2 Because          │
├────────────────────────┼──────────────────────────────────┤
│ Multiple parallel RPCs │ Multiplexing (streams)           │
│ on one connection      │ HTTP/1.1 can't do this           │
├────────────────────────┼──────────────────────────────────┤
│ Bidirectional streaming│ HTTP/2 streams are full-duplex   │
│ (client ↔ server)      │ HTTP/1.1 is request→response    │
├────────────────────────┼──────────────────────────────────┤
│ Efficient binary data  │ HTTP/2 binary framing            │
│ (Protocol Buffers)     │ HTTP/1.1 is text-based           │
├────────────────────────┼──────────────────────────────────┤
│ Header compression     │ HPACK (HTTP/2)                   │
│ (metadata per call)    │ HTTP/1.1 repeats headers fully   │
├────────────────────────┼──────────────────────────────────┤
│ Stream cancellation    │ RST_STREAM frame (HTTP/2)        │
│                        │ HTTP/1.1 = close connection      │
└────────────────────────┴──────────────────────────────────┘
```

### Explain gRPC

#### Mental model
```
REST: "Send an HTTP request with JSON, parse response manually"
gRPC: "Call a function on another server as if it's local code"

// REST (what it feels like)
const response = await fetch('http://order-service:3000/api/orders', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ userId: 42, items: [...] })
});
const order = await response.json(); // hope the shape is right...

// gRPC (what it feels like)
const order = await orderService.createOrder({ userId: 42, items: [...] });
// ↑ Looks like a local function call. Typed. Auto-completed by IDE.
// But it actually calls another machine over the network.

```

#### architecture

```
┌──────────┐  REST/GraphQL   ┌───────────────────────────────────┐
│  Browser │ ◄──────────────► │          API Gateway              │
└──────────┘                  └──────────┬──────────┬─────────────┘
                                         │          │
                                   gRPC  │    gRPC  │
                                         ▼          ▼
                              ┌───────────┐  ┌─────────────┐
                              │Order Svc  │  │Payment Svc  │
                              └─────┬─────┘  └─────────────┘
                                    │ gRPC
                                    ▼
                              ┌───────────┐
                              │Inventory  │
                              └───────────┘

Browser: REST (readable, standard)
Backend: gRPC (fast, typed, streaming)
```

#### When to Use gRPC vs REST

| Use gRPC | Use REST |
| :-- | :-- |
| Service ↔ Service (backend) | Browser ↔ Server (frontend) |
| High-throughput (thousands of calls/sec) | Public APIs (human-readable) |
| Need streaming | Simple CRUD |
| Strict contracts between teams | Flexibility / rapid prototyping |
| Performance matters (binary) | Easy debugging (curl, Postman) |
| Polyglot services (Go ↔ Node ↔ Java) | Single language ecosystem |


REST is an architectural style, 
SOAP is a protocol, 
GraphQL is a specification, 
gRPC is a framework, 
and tRPC is a library — they operate at different abstraction levels but all serve the same goal: defining how services communicate. 
They all run on top of actual transport protocols like HTTP and TCP.


### Unix Socket vs TCP/IP Socket

|  | Unix Socket | TCP/IP Socket |
| :-- | :-- | :-- |
| Адрес | Путь к файлу (/tmp/app.sock) | IP + Port (127.0.0.1:3000) |
| Область | Только одна машина | Любые машины (сеть) |
| Скорость | Быстрее (~2-3x) | Медленнее (network stack overhead) |
| Overhead | Минимальный | TCP headers, checksums, routing |
| Безопасность | File permissions (chmod) | Firewall, TLS, port exposure |
| Когда использовать | Процессы на одном сервере | Процессы на разных серверах |

Unix sockets provide faster IPC (inter-process communication) on the same machine by bypassing the entire TCP/IP network stack — data passes directly through the kernel via a file path. TCP/IP sockets go through the full network stack (even on localhost) but work across machines over the network. Use Unix sockets for local same-machine communication (NGINX→app, app→DB); use TCP/IP when processes are on different hosts.
