## Modern Frontend Rendering Techniques

#### The Evolution
```
2000s:  MPA (server renders everything)
2010s:  SPA/CSR (client renders everything)
2015+:  SSR (server renders, client hydrates)
2020+:  SSG, ISR, Streaming, RSC, Islands, Partial Hydration
2024+:  PPR (mixing static + dynamic in one page)
```

```
| Technique | Where HTML Generated | When | JS to Client |
| :-- | :-- | :-- | :-- |
| MPA | Server | Every request | Minimal |
| CSR (SPA) | Browser | Runtime (client) | Everything |
| SSR | Server | Every request | Full hydration |
| SSG | Server | Build time | Full hydration |
| ISR | Server | Build + revalidation | Full hydration |
| Streaming SSR | Server | Request (chunked) | Progressive hydration |
| RSC | Server | Request | Zero for server components |
| Islands | Server + Client | Mixed | Only interactive parts |
| PPR | Server | Build + request (mixed) | Minimal |
```


#### 1. MPA — Multi-Page Application (Traditional)
```
Every click = full page reload from server.

Browser: click link → Server: render HTML → Browser: full page load
Browser: click link → Server: render HTML → Browser: full page load

PHP, Rails, Django, plain Express templates.

✅ Simple, great SEO, fast first paint
✅ Minimal JS
❌ Full page reload on every navigation
❌ Slow transitions, no app-like feel
```

#### 2. CSR — Client-Side Rendering (SPA)

```
Server sends empty HTML + big JS bundle.
Browser downloads JS → JS builds entire page.

Server response:
  <html>
    <body>
      <div id="root"></div>       ← empty!
      <script src="app.js"/>      ← 500KB JS
    </body>
  </html>

Browser:
  1. Download HTML (empty)
  2. Download app.js (big)
  3. Execute JS
  4. Fetch data from API
  5. Render UI
  
  User sees: blank → spinner → content

Timeline:
  [blank page]──[download JS]──[execute]──[fetch data]──[render]
  0ms           200ms          800ms       1200ms        1500ms
                                                          ↑
                                                    User sees content

✅ Rich interactivity, app-like feel
✅ Fast subsequent navigations (no reload)
❌ Slow initial load (download + parse + execute JS)
❌ Bad SEO (empty HTML for crawlers)
❌ Bad on slow devices/networks
```

#### 3. SSR — Server-Side Rendering
```
Server renders FULL HTML → sends to browser → browser hydrates.

Server response:
  <html>
    <body>
      <div id="root">
        <h1>Dashboard</h1>         ← real content!
        <div class="stats">...</div>
        <button>Click me</button>  ← visible but NOT interactive yet
      </div>
      <script src="app.js"/>
    </body>
  </html>

Browser:
  1. Receive full HTML → user SEES content immediately
  2. Download JS
  3. Hydrate (attach event listeners to existing HTML)
  4. Now interactive

Timeline:
  [full HTML visible]──[download JS]──[hydrate]──[interactive]
  200ms                 400ms          800ms       1000ms
  ↑                                                ↑
  User sees content                           User can click

✅ Fast first paint (real HTML)
✅ Good SEO (crawlers see content)
❌ Server load (render every request)
❌ TTFB slower (server must render)
❌ Hydration cost (download full JS, re-process DOM)
```

#### 4. SSG — Static Site Generation

```
HTML generated at BUILD TIME, served as static files.

Build time (npm run build):
  page1.html ← pre-rendered with data
  page2.html ← pre-rendered with data
  page3.html ← pre-rendered with data

Deploy: push HTML files to CDN

User request → CDN serves pre-built HTML → instant!

Timeline:
  [HTML from CDN]──[hydrate]──[interactive]
  50ms              300ms       500ms
  ↑
  Fastest possible first paint (CDN edge)

✅ Fastest possible load (static files on CDN)
✅ Cheapest (no server, just CDN)
✅ Great SEO
❌ Data stale until next build
❌ Build time grows with pages (10K pages = slow build)
❌ Can't show user-specific content
```

#### 5. ISR — Incremental Static Regeneration

```
SSG + automatic revalidation in background.

First request:  serve cached static page
Background:     re-generate page if stale (time-based)
Next request:   serve freshly generated page

export async function getStaticProps() {
  const data = await fetchProducts()
  return {
    props: { data },
    revalidate: 60  // re-generate every 60 seconds
  }
}

Timeline for returning visitor:
  [cached HTML from CDN]──[hydrate]──[interactive]
  50ms                     300ms       500ms
  
  (meanwhile server regenerates page for next visitor)

✅ CDN speed + fresh data
✅ No full rebuild needed
✅ Scales to millions of pages
❌ Data can be up to N seconds stale
❌ Next.js specific (mostly)
```

#### 6. Streaming SSR

```
Instead of waiting for ENTIRE page to render on server,
STREAM chunks as they're ready.

Traditional SSR:
  Server: [render header]──[render content]──[fetch slow API]──[render footer]
  Browser: ──────────── waiting ──────────────────── [receive ALL at once]

Streaming SSR:
  Server: [render header] → SEND
          [render content] → SEND
          [fetch slow API...] → loading placeholder SENT
          [slow API done] → SEND replacement
  
  Browser sees content PROGRESSIVELY:
    100ms: header appears
    200ms: main content appears
    300ms: skeleton/loading for slow part
    800ms: slow part streams in and replaces skeleton

// React 18 + Next.js App Router
export default async function Page() {
  return (
    <div>
      <Header />                          {/* streams immediately */}
      <MainContent />                     {/* streams immediately */}
      <Suspense fallback={<Skeleton />}>
        <SlowDataComponent />             {/* streams when ready */}
      </Suspense>
    </div>
  )
}

✅ Fastest perceived performance (progressive)
✅ Slow API doesn't block entire page
✅ Works with React Suspense
❌ More complex server setup
❌ Not all hosting supports streaming
```

#### 7. RSC — React Server Components
```
Components that run ONLY on server. Zero JS sent to client.

// This component runs on SERVER only
// NO JavaScript shipped to browser for this
async function ProductList() {
  const products = await db.query('SELECT * FROM products')
  
  return (
    <ul>
      {products.map(p => <li key={p.id}>{p.name}</li>)}
    </ul>
  )
}

// This component needs interactivity → client
'use client'
function AddToCartButton({ productId }) {
  const [added, setAdded] = useState(false)
  return <button onClick={() => setAdded(true)}>Add</button>
}

// Page mixes both
export default function Page() {
  return (
    <div>
      <ProductList />           {/* server: 0 KB JS to client */}
      <AddToCartButton id={1} /> {/* client: only this JS shipped */}
    </div>
  )
}

RESULT:
  ProductList: rendered on server, HTML sent, NO JS bundle
  AddToCartButton: JS shipped for interactivity

  Traditional SSR: ship JS for EVERYTHING (hydrate all)
  RSC: ship JS ONLY for interactive parts

✅ Dramatically smaller JS bundles
✅ Direct database/filesystem access in components
✅ No API layer needed for read operations
✅ Server-only code never reaches client (secure)
❌ New mental model (server vs client boundary)
❌ Can't use useState/useEffect in server components
❌ Currently React + Next.js mostly
```

#### 8. Islands Architecture
```
Page is static HTML. Only "islands" of interactivity get JS.

┌─────────────────────────────────────────┐
│  Static Header (no JS)                   │
├─────────────────────────────────────────┤
│  Static Article Content (no JS)          │
│  Just HTML + CSS                         │
│                                          │
│  ┌─────────────────┐                    │
│  │ 🏝 Interactive   │ ← Island: has JS  │
│  │ Search Widget    │   (only this part) │
│  └─────────────────┘                    │
│                                          │
│  More static content...                  │
│                                          │
│  ┌─────────────────┐                    │
│  │ 🏝 Interactive   │ ← Island: has JS  │
│  │ Comment Form     │   (only this part) │
│  └─────────────────┘                    │
│                                          │
│  Static Footer (no JS)                   │
└─────────────────────────────────────────┘

JS loaded: only for 2 islands (~20KB)
vs SPA: JS for entire page (~500KB)

✅ Minimal JS (only interactive parts)
✅ Instant page load (mostly static)
✅ Great for content-heavy sites
❌ Less suitable for highly interactive apps (dashboards)
❌ Islands don't easily share state
```

#### 9. PPR — Partial Prerendering (Next.js 14+, Cutting Edge)

```
Single page = static shell + dynamic holes.

BUILD TIME:                        REQUEST TIME:
┌─────────────────────┐           ┌─────────────────────┐
│  Header (static) ✅  │           │  Header (static) ✅  │
│  Nav (static) ✅     │           │  Nav (static) ✅     │
│  ┌───────────────┐  │           │  ┌───────────────┐  │
│  │  [HOLE]       │  │    →      │  │ User: John    │  │
│  │  dynamic user │  │  filled   │  │ Cart: 3 items │  │
│  │  content      │  │  at edge  │  │               │  │
│  └───────────────┘  │           │  └───────────────┘  │
│  Footer (static) ✅  │           │  Footer (static) ✅  │
└─────────────────────┘           └─────────────────────┘

Static parts: served from CDN (instant)
Dynamic holes: filled at request time (streaming)

= SSG speed + SSR personalization in ONE page

✅ Best of all worlds
❌ Very new, still experimental
```

### Decision Matrix
```
Static content site (blog, docs)?
  → SSG or Astro (Islands)

Marketing site + some interactivity?
  → Islands (Astro) or SSG + hydration

E-commerce (SEO + dynamic)?
  → SSR + Streaming or ISR

Dashboard (highly interactive, auth-gated)?
  → CSR (SPA) or RSC

Social media / content + interaction?
  → RSC + Streaming SSR

Real-time app (chat, trading)?
  → CSR (SPA) + WebSocket

```
