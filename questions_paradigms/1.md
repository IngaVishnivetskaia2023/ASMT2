### Why do we need at all programming paradigms?

Programming paradigms exist to manage complexity. As applications grow, a single file becomes impossible to reason about, maintain, test, or collaborate on — human cognitive capacity is limited. Paradigms (OOP, functional, procedural) provide constraints and mental models that enforce structure, separation of concerns, and predictable code organization. These constraints enable reusability, testability, safe refactoring, and team collaboration at scale. Without them, any non-trivial application becomes unmaintainable — not because the machine cares, but because humans need boundaries to manage complexity.

### What is imperative approach?

Imperative programming describes **HOW** to do something — step-by-step instructions that mutate state, in a specific order. 
You explicitly tell the machine each operation to perform, like a recipe.

```
// Imperative: HOW to filter
const numbers = [1, 2, 3, 4, 5];
const result = [];
for (let i = 0; i < numbers.length; i++) {
  if (numbers[i] > 3) {
    result.push(numbers[i]);
  }
}

// Declarative (contrast): WHAT I want
const result = numbers.filter(n => n > 3);
```

The imperative approach controls the iteration, the condition check, and the mutation explicitly — the programmer manages all state transitions manually.

### Is procedural approach is the same as imperative?

No, but they're related. Imperative is the broad category — any code that describes step-by-step state mutations. 
Procedural is a specific style within imperative that organizes those steps into named procedures (functions/subroutines) for reuse and structure.

All procedural code is imperative, but not all imperative code is procedural — you can write imperative code as one flat sequence without any function organization (like a raw script). Procedural adds the concept of breaking imperative logic into callable, reusable units. 
Think of it as: imperative = "step by step", procedural = "step by step, organized into named procedures."

### Which FE frameworks are declarative vs imperative

**Declarative:** React, Vue, Angular, Svelte — you describe what the UI should look like for a given state, and the framework handles how to update the DOM. You write `<div>{items.map(i => <Item />)}</div>` — not manual DOM manipulation steps.

**Imperative:** jQuery and vanilla DOM API — you explicitly command each mutation: `$('#list').append('<li>')`, `document.createElement()`, `element.classList.add()`. You manage every step of DOM transformation yourself.

The industry moved toward declarative because it eliminates manual DOM bookkeeping, reduces bugs from state/UI desynchronization, and scales better for complex UIs — the framework reconciles desired state with actual DOM for you.

### Name Pros/Cons of declarative vs imperative and where each fits in a modern React + Node.js fullstack context

**Declarative pros:** Easier to reason about (describe outcome, not steps), 
less bug-prone for complex state/UI sync, more readable and maintainable, 
enables framework optimizations (React reconciliation, memoization).

**Declarative cons:** Performance overhead (abstraction layer), less fine-grained control, 
harder to debug when abstraction leaks, learning curve for mental model shift.

**Imperative pros:** Full control, predictable performance, direct and efficient for simple sequential tasks, no abstraction overhead.

**Imperative cons:** Harder to maintain at scale, error-prone state management, more code for complex UI, difficult to reason about as complexity grows.

**Where each fits in React + Node.js:**

| Layer | Approach | Example |
| :-- | :-- | :-- |
| React components / UI | Declarative | JSX describes desired output |
| React hooks internals / refs | Imperative | ref.current.focus(), manual DOM |
| Node.js scripts / CLI tools | Imperative/Procedural | Step-by-step file processing |
| Node.js with streams/Express middleware | Declarative-ish | Compose pipeline, describe behavior |
| Database queries (SQL, ORMs) | Declarative | Describe WHAT data, not HOW to fetch |
| Build configs (Webpack, ESLint) | Declarative | Describe desired outcome |

### What is OOP and its four pillars?

OOP (Object-Oriented Programming) is a paradigm that **organizes code around objects** — data structures that **bundle state (properties) and behavior (methods)** together, modeling real-world entities and their interactions.

#### Four pillars:

**Encapsulation** — bundling data and methods together, hiding internal state behind a public interface. Outside code interacts through defined methods, not direct property access.

**Abstraction** — exposing only essential complexity, hiding implementation details. Consumer uses car.start() without knowing ignition internals.

**Inheritance** — creating new classes based on existing ones, reusing and extending behavior. Child class inherits parent's properties/methods and can override them.

**Polymorphism** — same interface, different implementations. Multiple classes implement the same method differently; calling code doesn't need to know which specific class it's working with (shape.area() works for Circle, Square, Triangle).

### How polymorphism works in TypeScript?

#### Interface-based (most common in TS/FE):

```
interface Shape {
  area(): number;
}

class Circle implements Shape {
  constructor(private radius: number) {}
  area() { return Math.PI * this.radius ** 2; }
}

class Square implements Shape {
  constructor(private side: number) {}
  area() { return this.side ** 2; }
}

// Polymorphic — doesn't care which shape
function printArea(shape: Shape) {
  console.log(shape.area()); // same interface, different behavior
}
```

#### 2. Inheritance-based (method overriding):

```
class Animal {
  speak() { return 'silence'; }
}
class Dog extends Animal {
  speak() { return 'woof'; } // overrides parent
}
```

#### 3. Union types / ad-hoc polymorphism (TS-specific):

```
function format(value: string | number): string {
  return typeof value === 'string' ? value.trim() : value.toFixed(2);
}
```

### Explain Static and Dynamic Polymorphism

#### Dynamic Polymorphism in JS (How It Actually Works)
At runtime, when you call `obj.method()`, the JS engine:

- Looks at the object itself for method
- If not found → walks up the prototype chain
- Calls the first method it finds

```
class Shape {
  area() { return 0; }
}

class Circle extends Shape {
  constructor(r) { super(); this.r = r; }
  area() { return Math.PI * this.r ** 2; } // overrides Shape.area
}

class Square extends Shape {
  constructor(s) { super(); this.s = s; }
  area() { return this.s ** 2; } // overrides Shape.area
}

function totalArea(shapes) {
  // At RUNTIME, engine looks up each object's prototype
  // to find the correct area() — EVERY SINGLE CALL
  return shapes.reduce((sum, shape) => sum + shape.area(), 0);
}

// Engine doesn't know types ahead of time
// It resolves shape.area() dynamically for each object
totalArea([new Circle(5), new Square(3), new Circle(2)]);
```

#### Under the hood (V8 prototype lookup):

```
circle.area() called:
  → Does circle own "area"? NO
  → Check circle.__proto__ (Circle.prototype) → FOUND! Call it.

// This lookup happens at RUNTIME for every call
// (V8 optimizes with "hidden classes" / inline caches, 
//  but conceptually it's dynamic)
```

#### Duck typing — no inheritance needed:
```
// These have NO shared parent — still polymorphic
const circle = { area() { return 78.5; } };
const square = { area() { return 9; } };
const triangle = { area() { return 6; } };

// Works! JS doesn't check ancestry — only "does .area() exist?"
totalArea([circle, square, triangle]);
```

#### Static Polymorphism in TS — What Happens at Compile Time

#### 1. Function Overloads

```
// YOU WRITE (TypeScript):
function createElement(tag: 'div'): HTMLDivElement;
function createElement(tag: 'span'): HTMLSpanElement;
function createElement(tag: 'input'): HTMLInputElement;
function createElement(tag: string): HTMLElement {
  return document.createElement(tag);
}

const div = createElement('div');   // TS KNOWS this is HTMLDivElement
const input = createElement('input'); // TS KNOWS this is HTMLInputElement
// Resolved at COMPILE time — TS picks correct return type

// COMPILED JS OUTPUT:
function createElement(tag) {
  return document.createElement(tag); // just ONE function, no overloads
}
// All overload signatures GONE. Runtime has no idea.
```

#### What the compiler does:
```
Compile time:
  createElement('div') → matches overload 1 → return type: HTMLDivElement
  createElement('input') → matches overload 3 → return type: HTMLInputElement
  
  Compiler resolves which signature matches BEFORE code runs.
  Then erases all signatures, keeps only implementation.
```

Polymorphism is the mechanism that makes the Open/Closed Principle work.
So the relationship is: polymorphism is the tool, Open/Closed is the principle it serves. You implement OCP through polymorphic interfaces — new implementations extend the system without touching existing consumers.

### Explain Functional Programming and its core principles

**Core idea:** Build programs by composing pure functions — treating computation as evaluation of mathematical functions, avoiding mutable state and side effects.

#### 1. Pure Functions
Same input → always same output, no side effects.
```
// Pure
const add = (a, b) => a + b;

// Impure (depends on external state)
let tax = 0.2;
const addTax = (price) => price + price * tax;
```

#### 2. Immutability
Never mutate data — create new copies instead.
```
// Mutating (bad in FP)
arr.push(4);

// Immutable (FP way)
const newArr = [...arr, 4];
```

#### 3. First-Class & Higher-Order Functions
Functions are values — passed as arguments, returned from other functions.
```
const double = (x) => x * 2;
const map = (fn, arr) => arr.map(fn);
map(double, [1, 2, 3]); // [2, 4, 6]
```

#### 4. Function Composition
Build complex behavior by combining simple functions.
```
const compose = (f, g) => (x) => f(g(x));
const addOne = (x) => x + 1;
const double = (x) => x * 2;
const addOneThenDouble = compose(double, addOne);
addOneThenDouble(3); // 8
```

#### 5. Avoiding Side Effects / Declarative Style
Describe WHAT, not HOW. Push side effects to the edges of the system.


#### Other concepts
| Concept | Meaning |
| :-- | :-- |
| Referential transparency | Expression can be replaced with its value without changing behavior |
| Closures | Functions capturing their lexical scope (enables partial application) |
| Currying | f(a, b) → f(a)(b) — transform multi-arg into chain of single-arg |
| Recursion over loops | FP prefers recursion (no mutation of loop counter) |
| Monads (advanced) | Wrapping side effects in a composable container (Promise is a monad-like) |

#### Spectrum of FP Adoption in Production
```
Light FP (90% of projects)          Heavy FP (rare)
│                                    │
▼                                    ▼
map/filter/reduce    Lodash/fp     Ramda      fp-ts      Haskell-like
immutable updates    compose/pipe  currying   monads     pure everything
pure components      point-free    lenses     Either/Option
                                              Task/IO

```


## Reactive Programming

Reactive programming models asynchronous data as **composable streams (Observables)** with declarative transformation operators — the runtime handles timing, cancellation, and propagation while you describe the data flow pipeline. 
RxJS is the standard JS implementation, heavily used in Angular.

#### Where It's Used in Production
| Context | How |
| :-- | :-- |
| Angular | Built on RxJS — HttpClient returns Observables, reactive forms, router events |
| Real-time data | WebSocket streams, live dashboards, stock tickers |
| Complex UI interactions | Drag & drop, autocomplete, infinite scroll |
| State management | NgRx (Angular), Redux-Observable |
| Node.js | Stream processing, backpressure handling |
| React (less common) | RxJS for complex async, though hooks/React Query preferred |

#### How It Differs from Event-Driven
```
EVENT-DRIVEN (addEventListener):
  • Register callback for specific event
  • No transformation pipeline
  • Manual state management between events
  • No built-in cancellation/completion

REACTIVE (Observable):
  • Events are just one source type
  • Rich transformation/combination operators
  • State derived from stream composition
  • First-class cancellation, error handling, completion
  • Can combine multiple async sources declaratively
```


## Observable in Angular: example

#### Search Autocomplete
```
// search.component.ts
@Component({
  template: `
    <input [formControl]="searchControl" placeholder="Search...">
    <div *ngFor="let result of results$ | async">
      {{ result.name }}
    </div>
  `
})
export class SearchComponent implements OnInit {
  searchControl = new FormControl('');
  results$: Observable<SearchResult[]>;

  constructor(private http: HttpClient) {}

  ngOnInit() {
    this.results$ = this.searchControl.valueChanges.pipe(
      debounceTime(300),
      distinctUntilChanged(),
      filter(term => term.length > 2),
      switchMap(term => this.http.get<SearchResult[]>(`/api/search?q=${term}`))
    );
  }
}
```

#### Runtime Memory Model — What Exists

```
┌─────────────────────────────────────────────────────┐
│  ANGULAR RUNTIME                                     │
│                                                      │
│  FormControl "searchControl"                         │
│    └─ valueChanges: Subject (hot observable)         │
│        └─ Internally calls .next(value) on every     │
│           input event                                │
│                                                      │
│  Pipeline (created once in ngOnInit):                │
│  ┌─────────────────────────────────────────────┐    │
│  │  valueChanges                                │    │
│  │    → DebounceTimeSubscriber (holds timer)    │    │
│  │      → DistinctSubscriber (holds prev value) │    │
│  │        → FilterSubscriber (checks length)    │    │
│  │          → SwitchMapSubscriber               │    │
│  │              (holds current inner sub)        │    │
│  │            → async pipe subscriber           │    │
│  │                (triggers change detection)    │    │
│  └─────────────────────────────────────────────┘    │
│                                                      │
│  Each operator = an object that receives .next()     │
│  and decides whether to pass it forward              │
│                                                      │
└─────────────────────────────────────────────────────┘
```

#### Event Loop View — What Actually Happens
```
1. User presses key "t"
   └─ TASK: input event → Angular zone → FormControl.setValue()
      └─ Subject.next("React") → DebounceSubscriber.next("React")
         └─ Clears previous timer, sets new setTimeout(300ms)
      └─ MICROTASKS: Angular change detection (if needed)

2. 300ms later (no more keystrokes)
   └─ TASK: setTimeout fires → DebounceSubscriber passes "React"
      └─ DistinctSubscriber: "React" !== prev? YES → pass
         └─ FilterSubscriber: length > 2? YES → pass
            └─ SwitchMapSubscriber: cancel prev, new HTTP request
               └─ fetch() → Web API (network thread)
      └─ MICROTASKS: Angular zone stabilization

3. HTTP response arrives
   └─ TASK: network callback → SwitchMapSubscriber.inner.next(data)
      └─ async pipe receives data
         └─ markForCheck() → Angular re-renders list
      └─ MICROTASKS: change detection, view update
```
