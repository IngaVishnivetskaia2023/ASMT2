## SDLC Methodologies

### What SDLC Methodology is currently used in your project?

Scrumban — hybrid Scrum + Kanban with Lean elements and Shift-Left Testing.

| Your Practice | Methodology |
| :-- | :-- |
| Sprints с задачами | Scrum (time-boxed iterations) |
| Story points 1-21 (Fibonacci) | Scrum (relative estimation) |
| Grooming / estimation meetings | Scrum (backlog refinement) |
| Dev ставит оценку сам, может менять | Kanban (flexible, pull-based) |
| Детальные статусы в Jira (8 колонок) | Kanban (visual workflow, WIP tracking) |
| DM считает velocity из реальных данных | Kanban (Little's Law, throughput metrics) |
| BA решает что влезет в спринт по velocity | Scrum planning + Kanban forecasting |
| T-shirt sizing для Epics | Agile estimation technique |
| BA уточняет AC с клиентом | Scrum (Product Owner role / stakeholder collaboration) |
| Rough estimates прямо на звонке | Lean (just-in-time estimation, no waste) |
| Shift-left testing | Lean/DevOps practice |
| Dev тестирует вручную перед QA | Quality Engineering practice |

### Pure SCRUM
```
✅ FIXED SPRINT (time-box: 1-4 weeks, usually 2)
   Sprint starts → scope locked → sprint ends
   No tasks added mid-sprint by PM/client
   Only team can adjust scope (and only with PO agreement)

✅ ALL TASKS ESTIMATED BEFORE SPRINT START
   Every story has story points
   Estimated during Sprint Planning ceremony
   Planning Poker (team votes together)
   No unestimated work enters sprint

✅ DEFINED ROLES (strict)
   Product Owner — owns backlog, priorities, acceptance
   Scrum Master — facilitates, removes blockers, guards process
   Development Team — self-organizing, cross-functional
   (No "project manager", no "team lead" in pure Scrum)

✅ MANDATORY CEREMONIES (all of them, every sprint)
   Sprint Planning      — beginning of sprint (~4h for 2-week sprint)
   Daily Standup        — every day, 15 min max
   Sprint Review        — demo to stakeholders (end of sprint)
   Sprint Retrospective — team reflects (end of sprint)
   Backlog Refinement   — mid-sprint, prepare next sprint's stories

✅ SPRINT GOAL
   Every sprint has ONE clear goal
   "This sprint we deliver checkout flow"
   Team commits to the goal, not individual tasks

✅ DEFINITION OF DONE (DoD)
   Shared, agreed criteria for "done"
   Same for every story: coded + tested + reviewed + deployed

✅ VELOCITY = SUM OF COMPLETED STORY POINTS
   Only DONE stories count (partial = 0)
   Story 80% done = NOT counted in velocity

✅ POTENTIALLY SHIPPABLE INCREMENT
   Every sprint produces working software
   Could be released (even if you choose not to)
```

```
PURE SCRUM PROBLEMS:
  ❌ Rigid ceremonies take time (Planning, Review, Retro = ~8h per sprint)
  ❌ "No changes mid-sprint" doesn't fit fast-moving projects
  ❌ Estimation meetings (Planning Poker) = hours of debate
  ❌ Scrum Master role often feels unnecessary
  ❌ "Sprint failed" if stories not completed (demoralizing)
  ❌ Story must be 100% done or counts as 0 velocity

WHY SCRUMBAN WORKS BETTER (often):
  ✅ Keep sprints as time-boxes (structure)
  ✅ Allow flexibility mid-sprint (reality)
  ✅ Use real throughput data (accuracy)
  ✅ Estimate when useful, skip when wasteful (pragmatism)
  ✅ Ceremonies only when valuable (less waste)
```

#### Comparison of Methodologies

|  | Pure Scrum | Pure Kanban | Scrumban (Your Team) |
| :-- | :-- | :-- | :-- |
| Sprints | ✅ Fixed | ❌ None (continuous) | ✅ Flexible sprints |
| Estimation | ✅ Required (all stories) | ❌ None | ⚠️ When useful |
| Scope changes mid-sprint | ❌ Blocked | ✅ Anytime | ✅ Allowed |
| Ceremonies | ✅ All mandatory | ❌ None required | ⚠️ As needed |
| Roles | ✅ PO, SM, Team | ❌ No prescribed roles | ⚠️ Flexible (DM, BA) |
| Metrics | Velocity (SP/sprint) | Cycle time, throughput | Both |
| WIP limits | ❌ Not explicit | ✅ Strict | ⚠️ Informal |
| Board | Sprint board (reset each sprint) | Continuous flow board | Continuous with sprint overlay |
