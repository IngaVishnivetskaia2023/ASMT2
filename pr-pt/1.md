## IoC vs DI vs DIP

DIP is the SOLID principle saying 'depend on abstractions, not concretions.' 
IoC is the broader pattern where framework controls flow instead of your code ('don't call us, we'll call you' — React calling your components). 
DI is the specific technique of passing dependencies from outside (props, context, constructor) rather than creating them internally. 
In React: Context is the DI container, interfaces/types are the abstractions (DIP), and React's rendering lifecycle is IoC.

```
Dependency Inversion Principle (DIP) = DESIGN PRINCIPLE (from SOLID)
  "Depend on abstractions, not concrete implementations"

Inversion of Control (IoC) = BROAD PATTERN
  "Framework calls YOUR code, not you calling framework"

Dependency Injection (DI) = SPECIFIC TECHNIQUE
  "Pass dependencies in from outside instead of creating inside"

Relationship:
  DIP (principle) — WHY to invert dependencies
  IoC (pattern)   — general idea of inverting control
  DI  (technique) — HOW to achieve IoC/DIP in practice

  DIP is the REASON
  IoC is the CONCEPT
  DI is the IMPLEMENTATION
```

### 1. Inversion of Control (IoC)
#### "Don't call us, we'll call you" — The Hollywood Principle

#### Without IoC (YOU control everything)

```
// YOU manually control the entire lifecycle
// YOU decide when to create, render, update, destroy

const element = document.createElement('div')
element.innerHTML = '<h1>Hello</h1>'
document.body.appendChild(element)

// Later, YOU manually update
element.innerHTML = '<h1>Updated</h1>'

// YOU decide when to fetch
const data = await fetch('/api')
const html = buildHTML(data)
element.innerHTML = html

// YOU control EVERYTHING: creation, updates, DOM, timing

```

#### With IoC (REACT controls everything)

```
// YOU just describe WHAT to render
// REACT decides WHEN and HOW to render it

function App() {
  const [data, setData] = useState(null)

  useEffect(() => {
    fetch('/api').then(r => r.json()).then(setData)
  }, [])

  return <h1>{data?.title ?? 'Loading...'}</h1>
}

// You NEVER call:
//   "React, please render now"
//   "React, please update the DOM now"
//   "React, please unmount this"
//
// React calls YOUR component when IT decides to.
// React calls YOUR useEffect when IT decides to.
// React updates DOM when IT decides to.
```

```
// Array.map — YOU control iteration
for (let i = 0; i < items.length; i++) {
  process(items[i])
}

// Array.map — FRAMEWORK controls iteration (IoC)
items.map(item => process(item))
// You provide the WHAT (callback), framework controls WHEN/HOW


// Express — IoC
app.get('/api/users', (req, res) => {
  // YOU don't control when this runs
  // EXPRESS calls your function when request arrives
  res.json(users)
})


// React hooks — IoC
useEffect(() => {
  // YOU don't call this manually
  // REACT calls it after render, when dependencies change
  document.title = count
}, [count])

useState()      // React controls WHEN re-render happens
useCallback()   // React controls WHEN to memoize
useMemo()       // React controls WHEN to recompute
```

#### IoC Summary: metal model

```
NORMAL CONTROL:
  Your code calls library functions when YOU decide
  
  YOU → call → Library
  "I'm in charge"

INVERSION OF CONTROL:
  Framework calls YOUR code when IT decides
  
  Framework → calls → YOUR code
  "Framework is in charge, I just provide pieces"

REACT IS IoC:
  You give React components (pieces)
  React decides when to call them (rendering, reconciliation)
  You give React effects
  React decides when to run them
  You give React state updates
  React decides when to apply them (batching)
```

### 2. Dependency Injection (DI)
#### "Don't create your dependencies — receive them from outside"

#### Without DI (Component Creates Its Own Dependencies)
```
// ❌ Component CREATES its own dependency internally
function UserProfile() {
  // Hardcoded dependency — tightly coupled
  const api = new UserApiService('https://api.prod.com')
  const logger = new ConsoleLogger()
  const analytics = new GoogleAnalytics('UA-12345')

  const [user, setUser] = useState(null)

  useEffect(() => {
    api.getUser(42).then(setUser)
    logger.log('UserProfile mounted')
    analytics.track('profile_view')
  }, [])

  return <div>{user?.name}</div>
}

// PROBLEMS:
//   ❌ Can't test (always hits real API)
//   ❌ Can't reuse with different API/logger
//   ❌ Can't switch analytics provider
//   ❌ Changing API URL requires changing component
```

#### With DI — Via Props (Simplest Form)
```
// ✅ Dependencies INJECTED via props
function UserProfile({ api, logger, analytics }) {
  const [user, setUser] = useState(null)

  useEffect(() => {
    api.getUser(42).then(setUser)
    logger.log('UserProfile mounted')
    analytics.track('profile_view')
  }, [])

  return <div>{user?.name}</div>
}

// Production
<UserProfile
  api={new UserApiService('https://api.prod.com')}
  logger={new ConsoleLogger()}
  analytics={new GoogleAnalytics('UA-12345')}
/>

// Testing — inject mocks!
<UserProfile
  api={mockApi}
  logger={mockLogger}
  analytics={mockAnalytics}
/>

// Different environment
<UserProfile
  api={new UserApiService('https://api.staging.com')}
  logger={new FileLogger()}
  analytics={new MixpanelAnalytics()}
/>
```

#### Summary
```
WITHOUT DI:
  Component creates its own dependencies inside
  = tightly coupled, hard to test, hard to change

WITH DI:
  Dependencies passed IN from outside (props, context, hooks)
  = loosely coupled, testable, swappable

React DI mechanisms:
  Props           — simplest, explicit
  Context         — React's built-in DI container
  Custom hooks    — abstract and inject behavior
  HOCs            — wrap and inject (older pattern)
  Render props    — inject via function children (older)
```


### 3. Dependency Inversion Principle (DIP)

#### High-level modules should not depend on low-level modules. Both should depend on abstractions

#### Without DIP (Direct Dependency on Concrete Implementation)

```
// ❌ Component depends DIRECTLY on specific implementation

// Low-level module (concrete)
class LocalStorageCache {
  get(key) { return JSON.parse(localStorage.getItem(key)) }
  set(key, val) { localStorage.setItem(key, JSON.stringify(val)) }
}

// High-level module depends on LOW-LEVEL concrete class
function useUserSettings() {
  // Directly depends on LocalStorageCache
  const cache = new LocalStorageCache()  // ← TIGHT COUPLING

  const load = () => cache.get('settings')
  const save = (s) => cache.set('settings', s)
  return { load, save }
}

// PROBLEM:
//   Want to switch to SessionStorage? Change useUserSettings
//   Want to switch to IndexedDB? Change useUserSettings
//   Want to test without storage? Can't!
//
//   High-level (useUserSettings) depends on low-level (LocalStorageCache)
//
//   useUserSettings → LocalStorageCache (tight coupling)
```

#### With DIP (Both Depend on Abstraction)

```
// ✅ Define ABSTRACTION (interface/contract)
interface CacheStorage {
  get(key: string): any
  set(key: string, value: any): void
}

// Low-level implementations conform to abstraction
class LocalStorageCache implements CacheStorage {
  get(key) { return JSON.parse(localStorage.getItem(key)!) }
  set(key, val) { localStorage.setItem(key, JSON.stringify(val)) }
}

class SessionStorageCache implements CacheStorage {
  get(key) { return JSON.parse(sessionStorage.getItem(key)!) }
  set(key, val) { sessionStorage.setItem(key, JSON.stringify(val)) }
}

class InMemoryCache implements CacheStorage {
  private store = new Map()
  get(key) { return this.store.get(key) }
  set(key, val) { this.store.set(key, val) }
}

// High-level module depends on ABSTRACTION, not concrete class
// (Dependency Injection delivers the implementation)
const CacheContext = createContext<CacheStorage>(null!)

function useUserSettings() {
  const cache = useContext(CacheContext) // depends on INTERFACE
  const load = () => cache.get('settings')
  const save = (s: Settings) => cache.set('settings', s)
  return { load, save }
}

// USAGE — swap implementations without changing useUserSettings
// Production
<CacheContext.Provider value={new LocalStorageCache()}>
  <App />
</CacheContext.Provider>

// Testing
<CacheContext.Provider value={new InMemoryCache()}>
  <App />
</CacheContext.Provider>

// Different requirement
<CacheContext.Provider value={new SessionStorageCache()}>
  <App />
</CacheContext.Provider>
```

#### The Inversion Visualized

```
WITHOUT DIP (normal dependency direction):

  useUserSettings → depends on → LocalStorageCache
  (high-level)                   (low-level concrete)

  Change LocalStorageCache = break useUserSettings
  

WITH DIP (dependency INVERTED):

  useUserSettings → depends on → CacheStorage (interface)
                                      ↑
  LocalStorageCache → implements → CacheStorage (interface)
  SessionStorageCache → implements → CacheStorage (interface)
  InMemoryCache → implements → CacheStorage (interface)

  Both high-level AND low-level depend on ABSTRACTION
  = "Dependency Inversion" — the arrow FLIPPED for low-level module
  
  Change/swap implementation = useUserSettings unchanged!
```
