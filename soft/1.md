### 1. Task Delegation
Delegation is transferring **ownership** and **decision-making authority** for a task, not just handing off work. 

#### Can be delegated: 
- technical decisions within defined scope, 
- code reviews,
- spike investigations,
- documentation,
- mentoring juniors,
- running standups.

#### Cannot be delegated: 
- final accountability (you're still responsible for the outcome),
- performance reviews,
- confidential matters,
- tasks requiring your specific authority level.

The Delegation Poker / 7 Levels of Delegation range from **"Tell"** (I decide, you execute) through **"Consult"** (I decide after hearing you) to **"Delegate"** (you decide and act, just inform me). When delegating, always clarify the expected outcome, constraints, deadline, and reporting frequency — not the exact steps (that would be micromanagement). The appropriate delegation level depends on the delegate's competence and commitment (Situational Leadership model — D1 through D4).
Always provide context (the WHY) so the person can make **autonomous decisions** when unexpected situations arise.

#### 2. Delegation vs Assignment
Assignment is giving a person a defined task with clear steps — "implement this API endpoint per this spec." 
The assignee **executes but doesn't own decisions**. 
Delegation transfers **authority and ownership** — "you own the authentication module, decide the approach, report back on progress." 
❗ In assignment, the HOW is defined by you; 
in delegation, the WHAT is defined by you but HOW is decided by the delegate. 
Assignment is appropriate for junior developers who need structure (Situational Leadership S1 — Directing). 
Delegation is appropriate for mid/senior developers who have competence and need autonomy (S3-S4 — Supporting/Delegating). 
The key distinction: assignment develops execution skills, delegation develops decision-making and ownership skills. 
Moving team members **from receiving assignments to receiving delegations** is a core part of professional growth and empowerment.


#### 3. Task Decomposition & Managing Growth Ambitions

Decompose complex tasks using vertical slicing — **each slice delivers end-to-end value** — rather than horizontal splitting (frontend/backend separately). 

When a less senior teammate wants complex tasks, apply **scaffolded delegation**: 
- assign a well-defined subtask of the complex feature,
- provide guardrails (architecture decisions pre-made, interfaces defined),
- set check-in points (not just deadline),
- and review incrementally.

Create **a spike task first** — "spend 4 hours researching technology X, present findings" — this lets them learn without risking delivery. 
Use pair programming on the complex parts: they drive, you navigate — transferring knowledge while controlling risk. 
If the full task is too risky, split it: they do the new-technology PoC, you integrate it into production. 
Always frame it positively: "I want you to succeed on this, so let's build up to it with these steps" — this is growth-oriented feedback rather than gatekeeping. 
Track their progress through competency matrix to make growth visible and objective.


#### 4. Motivation Techniques
Use **intrinsic** motivation over **extrinsic** — Daniel Pink's framework: 
- Autonomy (let them choose HOW to solve),
- Mastery (progressively challenging tasks, visible skill growth),
- Purpose (connect their work to user/business impact).

Recognize contributions publicly and specifically — "your refactoring reduced production bugs by 40%" is better than "good job." 
Provide **stretch goals** — tasks slightly above current skill level that promote flow state (Csikszentmihalyi) — not too easy (boredom) and not too hard (anxiety).
For mentees specifically, make progress visible: "three months ago you couldn't do X, now you own it" — this builds self-efficacy. 
Use 1-on-1 meetings regularly to understand individual motivators — some want technical depth, others want leadership exposure, others want work-life balance. 
Remove demotivators first (unclear requirements, constant context-switching, blame culture) — Herzberg's hygiene factors must be met before motivators work. 
Create psychological safety (Amy Edmondson) where mistakes are learning opportunities, not punishment triggers.
