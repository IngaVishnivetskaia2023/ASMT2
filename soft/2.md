### Handling Urgent Mid-Sprint Customer Requests

```
Customer Urgent Request Arrives Mid-Sprint
│
├─── 🏉 SCRUM ──────── PROTECT the Sprint
│
├─── 🔀 SCRUMBAN ───── NEGOTIATE with WIP limits
│
└─── 📋 KANBAN ──────── PULL when capacity allows
```

#### SCRUM — "Protect the Sprint Commitment"
```
Sprint Boundary = SHIELD 🛡️

                    ┌─────────────────────────┐
  Urgent Request ──►│  Sprint Backlog (LOCKED) │
       ❌           │  ┌───┐ ┌───┐ ┌───┐     │
  Cannot inject     │  │ S1│ │ S2│ │ S3│     │
  directly!         │  └───┘ └───┘ └───┘     │
                    └─────────────────────────┘
```

In Scrum, the Sprint backlog is **protected**. No new work is injected mid-sprint **without the team's consent**. Here's the escalation path:
```
Step 1: PO receives the request
         │
Step 2: PO evaluates urgency & business value
         │
         ├── NOT truly urgent?
         │    └── Goes to Product Backlog
         │         └── Prioritized for NEXT Sprint
         │
         └── TRULY urgent / critical?
              │
         Step 3: PO negotiates with the team
              │
              ├── Option A: SWAP ─ Remove equal-sized item
              │   Story X (urgent) IN ←→ Story Y OUT
              │
              ├── Option B: ABORT Sprint
              │   (extreme case: sprint goal is obsolete)
              │   └── Sprint Planning for new Sprint
              │
              └── Option C: Wait for next Sprint
                  (if it's close enough)
```

#### Key Phrases to Use:
- "Sprint Goal integrity"
- "PO is the gatekeeper"
- "Swap, not add"
- "Team decides capacity impact"

#### SCRUMBAN — "Negotiate Within WIP Limits"

```
  Sprint exists BUT more flexible
  WIP Limits act as the REGULATOR

  ┌──────────┬──────────┬──────────┐
  │ TODO (5) │ WIP (3)  │   DONE   │
  ├──────────┼──────────┼──────────┤
  │ ┌──┐┌──┐│ ┌──┐┌──┐ │ ┌──┐     │
  │ │S1││S2││ │S3││S4│ │ │S5│     │
  │ └──┘└──┘│ └──┘└──┘ │ └──┘     │
  │ ┌──┐    │ ┌──┐     │          │
  │ │S6│    │ │🔥│←URGENT          │
  │ └──┘    │ └──┘     │          │
  └──────────┴──────────┴──────────┘
              WIP = 3 ← LIMIT HIT!
```

Scrumban is a hybrid. We have **sprint cadence for planning**, but use a **pull system with WIP limits**. An urgent request can be accommodated more flexibly:"

```
Urgent Request Arrives
         │
Step 1: PO evaluates priority
         │
Step 2: Check WIP limits
         │
         ├── WIP has capacity?
         │    └── PULL it in, prioritize at top of TODO
         │
         └── WIP is at limit?
              │
              ├── Option A: Expedite Lane (bypass WIP)
              │   ┌─────────────────────────────┐
              │   │ 🚨 EXPEDITE LANE (limit: 1) │ ← special
              │   ├──────────┬────────┬─────────┤
              │   │   TODO   │  WIP   │  DONE   │
              │   │  normal  │ normal │ normal  │
              │   └──────────┴────────┴─────────┘
              │
              ├── Option B: SWAP in TODO column
              │   Reprioritize, urgent goes to top
              │
              └── Option C: Wait until WIP frees up
                  (item finishes → pull urgent next)
```

- "WIP limits regulate flow"
- "Expedite lane for true emergencies"
- "Pull system allows flexibility"
- "Less rigid than Scrum, more structured than Kanban"


#### KANBAN — "Flow-Based, Pull When Ready"

```
  No Sprints! Continuous Flow
  Most flexible for urgent work

  ┌──────────┬──────────┬──────────┬────────┐
  │ BACKLOG  │ WIP (3)  │ REVIEW   │  DONE  │
  ├──────────┼──────────┼──────────┼────────┤
  │ ┌──┐     │ ┌──┐     │ ┌──┐    │ ┌──┐   │
  │ │🔥│ ←TOP│ │S1│     │ │S3│    │ │S5│   │
  │ └──┘     │ └──┘     │ └──┘    │ └──┘   │
  │ ┌──┐     │ ┌──┐     │         │        │
  │ │S7│     │ │S2│     │         │        │
  │ └──┘     │ └──┘     │         │        │
  └──────────┴──────────┴──────────┴────────┘
       ▲
       │ Urgent item placed at TOP
       │ Pulled NEXT when WIP frees up
```

Kanban has **no sprint boundaries**, so there's nothing to protect. The process naturally accommodates change through **prioritization and WIP limits**:"

```
Urgent Request Arrives
         │
Step 1: PO/Team Lead places it at TOP of backlog
         │
Step 2: Check WIP limits
         │
         ├── WIP has capacity?
         │    └── PULL immediately
         │
         └── WIP is at limit?
              │
              ├── Option A: Expedite Lane
              │   (true emergency, bypasses WIP)
              │
              ├── Option B: Wait for next pull
              │   (natural flow, pulled ASAP)
              │
              └── Option C: Swarm/Pair
                  (help finish current WIP faster
                   to free up a slot)
```

- "Continuous flow, no sprint to break"
- "Reprioritize the backlog"
- "WIP limits still apply"

#### mental model
```
Flexibility to Accept Urgent Work
──────────────────────────────────────►

  SCRUM          SCRUMBAN          KANBAN
  🔒              🔓                🔓
  Rigid           Hybrid            Fluid
  │                │                 │
  Swap/Abort      Expedite Lane    Reprioritize
  Sprint          + WIP flex       + Pull next
  │                │                 │
  PO negotiates   PO + WIP rules   PO places on top
  with team       govern flow      team pulls

  Protection:     Protection:      Protection:
  Sprint Goal     WIP Limits       WIP Limits only
  + WIP Limits
```
